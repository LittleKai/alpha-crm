# Hybrid Local-First Chatbot Design

**Date:** 2026-06-11

**Status:** Approved for implementation planning

## 1. Objective

Rebuild Alpha CRM's automatic chatbot as a complete hybrid local-first
workflow:

- Keyword rules, routing decisions, debounce, deduplication, handoff, and Zalo
  delivery run on the Windows local bridge.
- Cloud services remain authoritative for chatbot configuration, AI generation,
  subscription validation, quota accounting, and audit metadata.
- Full Zalo message history remains in the local SQLite database. The bridge
  sends only the context required for an AI request and bounded audit previews
  to the cloud.

## 2. Current Failure

The current production inbound route only persists conversations and messages.
It does not evaluate chatbot rules, call AI, create a reply command, or send a
reply. `matchChatbotRule` is used only by `/crm/chatbot/test`.

Local-first mode also reports an inbound metadata object without `content`,
while the cloud inbound route requires non-empty `accountId`, `threadId`, and
`content`. This causes metadata reports to fail with HTTP 400 and still would
not activate the chatbot if accepted.

The existing fields and UI imply behavior that is not implemented:

- `CrmConversation.chatbotEnabled` is editable but not consulted by inbound
  processing.
- `personalAudience` and `groupAudience` are stored but do not control
  production replies.
- Handoff logic exists only in the test endpoint.
- Chatbot logs are generated by the playground, not by real Zalo traffic.
- No production path returns a generated chatbot reply to the local Zalo
  account.

## 3. Architectural Decision

Use a hybrid local-first engine.

```text
Zalo inbound
  -> normalize and persist in local SQLite
  -> reject self, history, duplicate, or unsupported events
  -> debounce by account and thread for 3 seconds
  -> evaluate local conversation state and audience
  -> detect handoff
  -> match locally cached keyword rules
  -> otherwise request cloud AI
  -> send reply directly through zca-js
  -> persist outbound result and publish local SSE event
  -> sync bounded audit metadata to cloud
```

This architecture keeps deterministic and latency-sensitive work on the
machine that owns the Zalo session. Cloud AI remains centralized so subscription
and quota rules are not duplicated or bypassed.

## 4. Components

### 4.1 LocalChatbotEngine

The engine receives normalized real-time inbound events after local
persistence. It owns:

- Eligibility checks.
- Three-second per-conversation debounce.
- Duplicate and self-message rejection.
- Handoff detection.
- Keyword rule matching.
- Cloud AI fallback.
- Reply dispatch orchestration.
- Local and cloud audit state transitions.

History synchronization batches must never invoke the engine.

### 4.2 LocalChatbotConfigStore

The bridge stores the latest cloud chatbot snapshot locally:

- Global enabled state.
- AI enabled state and selected model.
- Personal and group audience settings.
- System, soul, and response prompts.
- Knowledge snippets.
- Active keyword rules ordered by priority.
- Global and rule-specific handoff keywords.
- Version and last successful synchronization time.

The bridge refreshes this snapshot:

- At authenticated local-session startup.
- Immediately after Flutter saves settings or changes rules.
- Periodically while the session remains online.

If configuration has never synchronized successfully, automatic replies remain
disabled. If a previously valid snapshot exists, keyword processing may
continue offline, but AI requests fail closed.

### 4.3 CloudChatbotApi

The cloud exposes agent-authenticated contracts for:

- Fetching the effective chatbot configuration and active rules.
- Generating an AI reply for an eligible inbound conversation.
- Recording bounded chatbot audit metadata.

The AI endpoint validates the active subscription, consumes quota using the
configured model cost, applies existing provider and refund behavior, and
returns the generated text plus audit identifiers.

The bridge sends only:

- Account, thread, and conversation identifiers.
- Thread type.
- The merged inbound message.
- A bounded recent text context needed for the response.
- Mention/quote eligibility metadata for group messages.

It does not upload attachments, credentials, cookies, local file paths, or the
complete SQLite history.

### 4.4 LocalChatbotDispatcher

The dispatcher sends chatbot replies directly through the active
`personal_zca` account. It:

- Uses the normalized account, thread, and thread type.
- Emits typing before the reply when supported.
- Creates a local optimistic outbound row.
- Reconciles the provider and client message IDs returned by zca-js.
- Publishes the same local SSE events used by Live Chat.
- Marks failed sends explicitly and never reports a failed reply as delivered.

The initial rebuilt workflow sends text only. Existing knowledge references may
influence the AI response, but automatic file or image selection is outside
this implementation.

### 4.5 ChatbotAuditSync

Every terminal decision produces an audit record:

- `keyword`
- `ai`
- `handoff`
- `none`
- `failed`

The cloud receives conversation identity, mode, matched rule ID where
applicable, bounded prompt/response previews, timestamps, status, and a
sanitized error code. Full messages and stack traces are not included.

## 5. Conversation State

SQLite stores chatbot state per account and thread:

- `enabled`
- `handoff`
- `disabled_by_operator`

It also stores:

- State reason.
- State update timestamp.
- Last processed provider message ID.
- Last chatbot reply timestamp.

New personal conversations inherit the effective global personal audience:

- `all`: enabled.
- `crmOnly`: enabled only when cloud metadata identifies the thread as a CRM
  customer.

Existing explicit local states are preserved during configuration refreshes.

An operator can explicitly enable the chatbot again after either handoff or
manual takeover.

## 6. Operator Takeover

After a manual operator message is delivered successfully, the bridge changes
the conversation to `disabled_by_operator`.

The state must not change when:

- The send fails.
- The outbound message was generated by the chatbot.
- A historical self-message is imported.
- A provider self-echo reconciles an existing chatbot message.

Flutter reads the effective local state for local-first conversations and
updates it through the bridge. Cloud conversation metadata may mirror the
state, but it is not the runtime authority for local-first delivery.

## 7. Handoff

Handoff keywords are normalized case-insensitively. Vietnamese matching also
uses a diacritic-insensitive comparison so phrases such as `nhân viên` and
`nhan vien` are equivalent.

When handoff is detected:

1. Do not evaluate a keyword rule or AI.
2. Change the conversation state to `handoff`.
3. Record a skipped handoff audit entry.
4. Publish a local conversation-state event for Flutter.
5. Do not send an automatic fallback message.

## 8. Group Eligibility

A group message is eligible only when all conditions are true:

- The group is managed by Alpha CRM.
- The effective group audience includes that group.
- The chatbot is enabled for the conversation.
- The inbound message mentions the connected Zalo account or quotes a message
  sent by that account.

`groupAudience` behavior:

- `none`: no group replies.
- `tagOnly`: managed groups are eligible when mention/quote conditions pass.
- `selected`: only explicitly selected managed groups are eligible, and the
  mention/quote conditions still apply.

Group events without a reliable mention or quote target fail closed.

## 9. Debounce And Deduplication

Real-time inbound text messages are buffered by `accountId + threadId` for
three seconds. New messages reset the timer. At expiry:

- Preserve chronological order.
- Join non-empty text content with newlines.
- Use the latest event as the reply target metadata.
- Process the merged input exactly once.

The engine rejects:

- Self-sent events.
- History synchronization events.
- Empty or non-text-only events in the initial implementation.
- Provider message IDs already marked as processed.
- Events whose account session is inactive.

The in-memory debounce map has a bounded size and is cleared when the local
session stops or is revoked.

## 10. Rule Evaluation

Rules are evaluated locally in ascending priority order using their configured
channel scope and match mode:

- `exact`
- `startsWith`
- `contains`

Matching is case-insensitive and diacritic-insensitive. The first eligible
match wins. A rule response is sent directly without consuming AI quota.

Business-hour configuration is honored when enabled. A rule outside its
configured hours is skipped rather than treated as a match.

## 11. AI Fallback

AI is requested only when:

- The conversation remains eligible.
- No handoff keyword matched.
- No keyword rule matched.
- AI is enabled.
- The cloud session and active CRM subscription are valid.

Recent local text context is bounded by both message count and total character
count before transmission. The cloud constructs the authoritative prompt from
saved settings and knowledge snippets.

If AI is unavailable, quota is exhausted, the request times out, or generation
fails:

1. Do not send a fallback response.
2. Record a failed audit entry.
3. Change the conversation to `handoff`.
4. Notify Flutter through a local state event.
5. Do not retry automatically.

## 12. Error Handling

Failures are isolated by stage:

- Configuration sync failure keeps the last valid snapshot.
- Local persistence failure prevents chatbot processing for that event.
- Rule evaluation failure records `failed` and hands off.
- Cloud AI failure records `failed` and hands off.
- Zalo send failure keeps the local outbound row failed, records `failed`, and
  hands off.
- Audit sync failure is queued locally and retried independently; it does not
  resend the Zalo reply.

All retryable audit records require a stable idempotency key. Reply sending
itself is never retried automatically after an ambiguous provider result.

## 13. Flutter Behavior

The existing Chatbot screen remains the management surface for settings,
rules, playground tests, and logs.

Required behavior changes:

- Saving settings or changing rules requests immediate bridge synchronization.
- The screen shows whether the bridge has an active configuration snapshot and
  its last synchronization time.
- Live Chat displays the effective local chatbot state.
- Enabling or disabling a local-first conversation updates the bridge first.
- A handoff or failed AI state is visible to the operator.
- Manual sends rely on the bridge to disable automation only after provider
  delivery succeeds.

The cloud playground remains a test tool and does not simulate local delivery.

## 14. Reference Findings

Deplao does not expose a standalone keyword-chatbot module, but its workflow
engine demonstrates the relevant production pattern:

- Inbound message triggers.
- Per-thread debounce and bounded buffers.
- Filtered workflow execution.
- Optional conversation history for AI.
- Structured run logging.
- Direct Zalo delivery through the active local account.

ZaloCRM provides a robust listener-to-persistence flow but no automatic reply
engine. Its useful reference is normalization and reliable real-time message
persistence, not chatbot behavior.

## 15. Testing Strategy

### Local Node Unit Tests

- Personal conversation inherits global eligibility.
- CRM-only personal audience rejects non-CRM threads.
- Operator send success disables the bot.
- Failed/manual-history/chatbot sends do not trigger operator takeover.
- Handoff matching handles Vietnamese with and without diacritics.
- Managed group mention and quote rules are enforced.
- Debounce merges messages in order and executes once.
- Duplicate, self, history, empty, and inactive-account events are ignored.
- Rule priority, scope, match mode, and business hours are honored.
- AI is called only after rule miss.
- AI and send failures produce handoff without fallback or automatic resend.

### Cloud Backend Contract Tests

- Agent configuration endpoint returns only the owning user's effective
  settings and active rules.
- Agent AI endpoint enforces device identity, subscription, quota, model cost,
  and quota refund on provider failure.
- Audit endpoint is idempotent and stores bounded previews.
- Existing local-first metadata ingestion accepts metadata without requiring
  full message content.
- Production inbound persistence does not accidentally execute a second cloud
  chatbot engine.

### Flutter Tests

- Settings/rule mutations request bridge synchronization.
- Bridge sync status and errors render correctly.
- Conversation state changes use the local bridge in local-first mode.
- Manual send does not optimistically disable the chatbot before confirmed
  delivery.
- Handoff and AI failure states render actionable operator status.

### Integration Verification

Run an end-to-end personal chat:

1. Keyword hit sends one local response without AI quota.
2. Rule miss sends one AI response and consumes the expected quota.
3. Multiple messages within three seconds produce one reply.
4. Human handoff keyword produces no reply.
5. Operator reply disables subsequent automation.
6. Re-enabling restores automation.
7. Cloud outage produces no reply and visible handoff.
8. Managed group replies only after valid mention or quote.

## 16. Success Criteria

The rebuild is complete when:

- A real inbound Zalo message can produce exactly one keyword or AI reply.
- Local-first inbound metadata no longer fails the cloud contract.
- Full chat history remains local except for bounded AI context.
- Manual takeover, handoff, audience, group, debounce, and duplicate rules are
  enforced.
- AI or Zalo failures never create false successful replies.
- Runtime decisions are observable in Flutter and cloud audit logs.
- Focused Node, backend, and Flutter tests pass, followed by full project
  verification.
