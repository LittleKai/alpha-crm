# Alpha CRM n8n, Facebook, TikTok, Instagram, WhatsApp, Telegram, and Webchat Integration Contract

## Current implementation in this repo

- Flutter adds the `/workflows` workspace with a workflow template catalog, n8n settings, and template install actions.
- The local `integration/zalo-bot-service` stores n8n settings at `.data/integrations/settings.json`, masks the API key for UI responses, creates n8n workflows through the n8n Public API, and dispatches inbound Zalo events to a configured n8n webhook.
- Per-account Zalo proxy metadata is now enforced when `personal_zca` credentials are loaded: the account setting proxy URL becomes the `agent` passed into `zca-js`.
- Facebook is represented as `facebook_page` in the channel capability matrix and template catalog. Built and shipped: Meta webhook **receiving** is cloud-owned (`alpha-studio-backend`); outbound **sending** happens directly from the local `zalo-bot-service` agent to the Graph API using a page access token that never leaves the local machine, exactly like Zalo.
- TikTok is represented as `tiktok` and mirrors the same adapter shape (`TiktokChannel`, structurally identical to `FacebookChannel`) and the same cloud-relay webhook pattern (`GET/POST /api/crm/tiktok/webhook`). Every TikTok-specific field/header/endpoint name (`account_id`, `x-tiktok-signature`, the TikTok Business Messaging API base URL) is an explicitly-commented **unverified placeholder** — it has not been checked against real TikTok Business Messaging API docs or live credentials, and must be re-verified before relying on it in production.
- Instagram is represented as `instagram` (Giai đoạn G) and, unlike TikTok, rides the **same real, already-verified Meta Graph API** as Facebook — same App/App Secret, same `X-Hub-Signature-256` scheme, same `entry[].messaging[]` webhook shape, distinguished only by `object: "instagram"` in the top-level payload. There is no placeholder uncertainty here (`InstagramChannel` in `integration/zalo-bot-service/src/channels/instagram-channel.ts`).
- WhatsApp is represented as `whatsapp` (Giai đoạn H) and also rides the **same real, already-verified Meta Graph API**, but the webhook payload shape is `entry[].changes[].value.messages[]` (WhatsApp Business Account format), not Messenger/IG's `entry[].messaging[]`; outbound `sendMessage()` posts to `https://graph.facebook.com/v19.0/{phone_number_id}/messages` with `messaging_product: 'whatsapp'` (`WhatsappChannel` in `integration/zalo-bot-service/src/channels/whatsapp-channel.ts`). Product decision: the 24h customer-service messaging window is **warn-only** on the Flutter UI (`enforce24hWindow` checkbox/tooltip) — no hard block in the backend or local agent, matching the existing unenforced pattern for Facebook/TikTok/Instagram.
- Telegram is represented as `telegram` (Giai đoạn I) and, unlike the Meta-based channels, has **no relation to the Meta Graph API at all**: outbound `sendMessage()` posts to `https://api.telegram.org/bot{token}/{method}` using the bot's own token, and inbound webhook verification uses an `x-telegram-bot-api-secret-token` header (set at `setWebhook` time) instead of an HMAC signature (`TelegramChannel` in `integration/zalo-bot-service/src/channels/telegram-channel.ts`). Webhook registration is automatic — the local bridge calls Telegram's `getMe` + `setWebhook` as soon as a bot's Bot Token is saved, unlike the manual dashboard configuration required for the Meta channels.
- Webchat is represented as `webchat` (Giai đoạn L) and inverts the usual direction entirely: the "other side" is an anonymous visitor's browser reached only via a `<script>` embed snippet on the customer's own website, so it has **no third-party provider at all** (no Meta/Telegram, no OAuth, no HMAC/secret-token webhook to verify) — the guest can only reach the **cloud backend** directly, never the local bridge. Auth is purely a random per-guest `sessionToken` (created client-side, stored in the visitor's `localStorage`), which doubles as both identity and bearer credential, matching `CrmConversation`'s existing unique index (`accountId` = widgetId, `threadId` = sessionToken). Realtime delivery uses a dedicated anonymous SSE hub (`webchatEventHub.js`, keyed by `` `${widgetId}:${sessionToken}` ``) — separate from the authenticated, per-CRM-user `crmEventHub` used by every other channel. Because arbitrary customer domains embed the widget, its public routes are mounted with their own permissive `cors({origin:true, credentials:false})` **before** the app's global CORS whitelist in `server/index.js`, rather than the origin-allowlist policy every other route uses. MVP scope is text-only, two-way chat (`WebchatChannel` in `integration/zalo-bot-service/src/channels/webchat-channel.ts`).
- Facebook, TikTok, Instagram, WhatsApp, Telegram, and Webchat all support multiple accounts/widgets per user (multiple Pages / TikTok accounts / IG accounts / WhatsApp phone numbers / Telegram bots / Webchat widgets), each its own row keyed by `(userId, channel, externalAccountId)`. The local bridge (`integration/zalo-bot-service/src/server.ts`) exposes `GET/POST /api/integrations/facebook/accounts` + `DELETE /api/integrations/facebook/accounts/:pageId` (mirrored for `tiktok/accounts`, `instagram/accounts`, `whatsapp/accounts`, `telegram/accounts`, and `webchat/accounts`), backing the Flutter list+detail settings screens (`facebook_settings_screen.dart`/`tiktok_settings_screen.dart`/`instagram_settings_screen.dart`/`whatsapp_settings_screen.dart`/`telegram_settings_screen.dart`/`webchat_settings_screen.dart`, the last also offering a "copy embed snippet" action); each save/delete also registers/deregisters the matching cloud `CrmChannelIntegration` row via `POST /api/crm/agent/channels/register` / `DELETE /api/crm/agent/channels/:id`. The Live Chat account-switcher dropdown (`live_chat_screen.dart`) merges these accounts (via `workflowAutomationProvider.state.facebookPages`/`.tiktokAccounts`/`.instagramAccounts`/`.whatsappAccounts`/`.telegramBots`/`.webchatWidgets`) alongside Zalo accounts so conversations from any Page/account/widget can be filtered independently.
- All chat data (Zalo, Facebook, TikTok, Instagram, WhatsApp, Telegram, Webchat) continues to be stored in the local SQLite `LocalChatStore` via `emitInboundMessage`. The cloud webhook/public route only keeps a durable Mongo backup copy and relays the raw event down to the desktop agent through the existing `CrmAgentCommand` + `/agent/commands/next` poll mechanism (`channel.message.relay` command type), so the agent can write it into local SQLite the same way it does for native Zalo events. For Webchat specifically, the outbound direction is inverted too: a staff reply must call **up** to the cloud (`relayWebchatOutboundMessage()` in `cloud-api.ts`, reusing the existing `x-agent-device-id`/`x-agent-secret` auth), which then pushes it out over the guest's SSE connection — every other channel sends directly from the local bridge to the third-party API instead.

## Required cloud backend endpoints

The local desktop backend is bound to `127.0.0.1`, so an outside n8n instance cannot reliably call it directly. n8n action callbacks must call the cloud backend, and the existing local agent polling loop should receive queued commands.

Required endpoints:

- `POST /api/crm/n8n/actions` — **not yet implemented.**
  - Auth: signed secret or tenant-scoped token issued by cloud.
  - Body: `{ action, channel, accountId?, pageId?, conversationId?, payload, idempotencyKey? }`.
  - Behavior: validate tenant, rate-limit risky actions, enqueue supported agent commands such as `zalo.message.send`.
- `POST /api/crm/agent/channels/register` — **implemented** (`server/routes/crm.js`).
  - Auth: `x-agent-device-id` + `x-agent-secret` (same auth as the rest of the agent-polling API), not a Flutter-facing endpoint.
  - Body: `{ channel, externalAccountId, appId?, verifyToken, appSecret, enabled? }`.
  - Behavior: called automatically by the local bridge (`zalo-bot-service/src/server.ts`) whenever the operator saves a complete, enabled Facebook, TikTok, or Instagram integration in the Flutter settings screen. Persists `verifyToken`/`appSecret` (encrypted at rest) on `CrmChannelIntegration` so the webhook routes below can verify the platform's signature — the page/account access token itself is never sent to the cloud.
- `GET /api/crm/agent/channels` — **implemented** (`server/routes/crm.js`), channel-agnostic, `agentAuthMiddleware`.
  - Behavior: lists every `CrmChannelIntegration` row owned by `req.crmDevice.userId` (`id`, `channel`, `externalAccountId`, `appId`, `enabled`), enabling multiple Facebook Pages/TikTok accounts/Instagram accounts to run side by side for one user.
- `DELETE /api/crm/agent/channels/:id` — **implemented** (`server/routes/crm.js`), channel-agnostic, `agentAuthMiddleware`.
  - Behavior: deletes one integration scoped to `userId` (404 if not owned/found). Called by the local bridge when a Page/account is removed from the Facebook/TikTok/Instagram settings screen, stopping that account's webhook traffic from generating further `CrmAgentCommand`s.
- `GET /api/crm/facebook/webhook` — **implemented** (`server/routes/channelWebhooks.js`).
  - Meta webhook verification with verify token.
- `POST /api/crm/facebook/webhook` — **implemented** (`server/routes/channelWebhooks.js`).
  - Verifies Meta's `X-Hub-Signature-256` against the stored `appSecret`, writes a durable `CrmConversation`/`CrmMessage` backup copy, and creates a `CrmAgentCommand{type:'channel.message.relay'}` so the desktop agent relays the event into local SQLite.
- `GET /api/crm/tiktok/webhook` — **implemented** (`server/routes/channelWebhooks.js`), mirrors the Facebook handshake shape. **Placeholder**: verify-token query param name is an unverified guess pending real TikTok docs.
- `POST /api/crm/tiktok/webhook` — **implemented** (`server/routes/channelWebhooks.js`), mirrors the Facebook flow: verifies an `x-tiktok-signature` HMAC-SHA256 against the stored `appSecret`, writes the same durable Mongo backup, and creates a `CrmAgentCommand{type:'channel.message.relay', payload:{channel:'tiktok', ...}}`. **Placeholder**: header name, payload shape (`account_id`, `messages[]`), and signature scheme are unverified guesses mirroring Facebook — re-check once real TikTok Business Messaging API docs/credentials are available.
- `GET /api/crm/instagram/webhook` — **implemented** (`server/routes/channelWebhooks.js`, Giai đoạn G). Same Meta webhook verification with verify token as Facebook (Instagram Direct rides the same Meta Graph API).
- `POST /api/crm/instagram/webhook` — **implemented** (`server/routes/channelWebhooks.js`, Giai đoạn G). Verifies Meta's `X-Hub-Signature-256` against the stored `appSecret` (same signature scheme as Facebook), writes a durable `CrmConversation`/`CrmMessage` backup copy, and creates a `CrmAgentCommand{type:'channel.message.relay', payload:{channel:'instagram', ...}}`.
- `GET /api/crm/whatsapp/webhook` — **implemented** (`server/routes/channelWebhooks.js`, Giai đoạn H). Same Meta webhook verification with verify token as Facebook/Instagram.
- `POST /api/crm/whatsapp/webhook` — **implemented** (`server/routes/channelWebhooks.js`, Giai đoạn H). Verifies Meta's `X-Hub-Signature-256` against the stored `appSecret` (same signature scheme as Facebook), but parses the WhatsApp Business Account payload shape (`entry[].changes[].value.messages[]`) rather than `entry[].messaging[]`. Writes a durable `CrmConversation`/`CrmMessage` backup copy and creates a `CrmAgentCommand{type:'channel.message.relay', payload:{channel:'whatsapp', ...}}`.
- `POST /api/crm/telegram/webhook/:botId` — **implemented** (`server/routes/channelWebhooks.js`, Giai đoạn I). POST-only — Telegram has no GET verify handshake. Verifies the `x-telegram-bot-api-secret-token` header against the stored per-bot `verifyToken` (no HMAC signature scheme, unlike the Meta channels), writes a durable `CrmConversation`/`CrmMessage` backup copy, and creates a `CrmAgentCommand{type:'channel.message.relay', payload:{channel:'telegram', ...}}`.
- `GET /api/public/webchat/:widgetId/config`, `GET /api/public/webchat/:widgetId/messages?sessionToken=`, `POST /api/public/webchat/:widgetId/messages`, `GET /api/public/webchat/:widgetId/events?sessionToken=` — **implemented** (`server/routes/webchatPublic.js`, Giai đoạn L), plus the static embed script at `GET /webchat/widget.js`. Unlike every other channel above, these routes have **no HMAC signature and no webhook secret-token check at all** — there is no upstream third-party provider to verify, so the only gate is the guest's own randomly-generated `sessionToken` (bearer-style, carried in the query/body, never a cookie) plus a per-IP and per-session in-memory sliding-window rate limit (60/min on config+history, 30/min on sends). `POST /:widgetId/messages` reuses the same `upsertConversationFromInbound` + `CrmAgentCommand{type:'channel.message.relay', payload:{channel:'webchat', ...}}` pipeline as the other channels; `GET /:widgetId/events` is a dedicated anonymous SSE stream (`webchatEventHub.js`) separate from the authenticated `crmEventHub` used elsewhere. A companion agent-authenticated relay branch in `server/routes/crm.js` (channel allowlist entry `'webchat'`) publishes staff replies back onto `webchatEventHub` so the guest's browser receives them in real time.

## Channel rules

- `zalo_personal`: personal-account operations remain behind the local agent and existing compliance guard.
- `zalo_oa`: official webhook/send only; no friend/group automation.
- `facebook_page`: official Meta Page/Messenger API only; no cookie login, no personal profile automation, no bulk send outside valid policy windows.
- `tiktok`: official TikTok Business Messaging API only (placeholder pending verification); no cookie login, no personal profile automation, no bulk send outside valid policy windows — same posture as `facebook_page`.
- `instagram`: official Meta Graph API (Instagram Direct) only, same real/verified API as `facebook_page` (no placeholder uncertainty); no cookie login, no personal profile automation, no bulk send outside valid policy windows.
- `whatsapp`: official WhatsApp Cloud API (Meta Graph API) only, same real/verified API family as `facebook_page`; no cookie login, no personal profile automation. The 24h customer-service messaging window is enforced as a **UI warn-only** checkbox (`enforce24hWindow`), not a hard backend/agent block — matches the existing unenforced posture of the other Meta channels.
- `telegram`: official Telegram Bot API only; no cookie login, no personal profile automation, no bulk send outside valid policy windows — same posture as `facebook_page`, despite having no Meta involvement.
- `webchat`: no third-party provider at all — the counterparty is an anonymous website visitor, gated only by their own random `sessionToken` plus IP/session rate limiting (no HMAC, no webhook secret-token, no domain allowlist, no CAPTCHA in v1); text-only MVP, no bulk send, no cookie login, no personal profile automation.

## n8n expectations

- Users bring an external n8n URL and API key.
- Alpha CRM creates workflows inactive by default; the operator reviews and activates in n8n.
- n8n webhook production URLs require the workflow to be active in n8n.
- n8n action nodes should call the cloud relay URL, not `127.0.0.1`.
