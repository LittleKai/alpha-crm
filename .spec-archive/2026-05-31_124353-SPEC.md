## Goal

Identify only the Deplao/9Meta patterns that are useful for Alpha CRM and define how to apply them without importing personal-account Zalo automation risk into the Flutter CRM product.

This SPEC replaces broader Zalo bot implementation planning. It is intentionally limited to transferable product/UI/architecture ideas from Deplao/9Meta.

---

## Context / Constraints

Alpha CRM is a Flutter CRM UI with Riverpod, GoRouter, token-driven design, and mock-first feature modules. Existing Zalo integration work already includes settings risk controls, a compliance guard, documentation, and a Node service skeleton.

Deplao/9Meta is an Electron desktop app that loads chat platforms in BrowserViews, supports profile/session management, quick replies, downloads/update panels, lock/settings, and a backend billing/license flow.

Apply only patterns that fit Alpha CRM's official, consent-based CRM direction. Do not port Electron BrowserView control, personal Zalo session automation, proxy rotation, seen/typing interception, QR login, or friend/group automation.

Relevant Alpha CRM files:

- `docs/zalo-integration-and-risk-controls.md`
- `docs/zalo-integration-installation-and-usage.md`
- `lib/features/settings/presentation/screens/settings_screen.dart`
- `lib/features/settings/providers/settings_provider.dart`
- `lib/shared/utils/zalo_compliance_guard.dart`
- `lib/features/zalo_integration/`
- `integration/zalo-bot-service/`

Relevant Deplao/9Meta reference files:

- `main.js` - native lifecycle, profile sessions, tray, downloads, updater, settings, proxy, BrowserView management.
- `renderer.js` - sidebar profile UI, modal flows, downloads/update panels, quick replies, auth/license UI.
- `preload.js` - quick reply injection and network-interception patterns. Only quick reply UX is transferable.
- `backend/src/server.js` and backend controllers - backend separation pattern for auth/license/payment concerns.

## Applicable Pattern Matrix

| Deplao/9Meta Pattern | Apply to Alpha CRM? | Alpha CRM adaptation |
|---|---:|---|
| Sidebar profile/account list | Yes | Reuse as inspiration for OA/Bot connection/account cards in Settings. Show connection status, label, last sync, and safe mode. Do not store personal Zalo sessions. |
| Per-profile settings modal | Yes | Adapt into structured Settings sections for backend URL, webhook path, risk controls, and approval thresholds. |
| Quick replies | Yes | Use for Live Chat and content templates. Operator should review before send; only use in inbound/recent-interaction conversations. |
| Downloads/status panel UX | Yes | Adapt for backend health, webhook status, queue status, and send history. |
| Update/status progress UI | Yes | Adapt as service status feedback and long-running campaign progress, not as app auto-update requirement. |
| App lock / sensitive settings | Yes | Use as product direction for protecting Zalo credentials, approval actions, and high-risk controls. |
| Backend boundary for license/payment | Yes | Use the same separation principle: secrets and enforcement live in backend service, Flutter sees only status/results. |
| BrowserView personal account sessions | No | Out of scope. Conflicts with official CRM integration direction. |
| Proxy rotation by profile | No | Out of scope. High-risk evasion signal. |
| Seen/typing blocking | No | Out of scope. Platform behavior interception is not a CRM requirement. |
| QR login/cookie/session reuse | No | Out of scope. Do not import into Alpha CRM. |
| Auto friend/group/member scraping flows | No | Keep existing Alpha CRM screens mock/test-only unless redesigned around official APIs and consent. |
