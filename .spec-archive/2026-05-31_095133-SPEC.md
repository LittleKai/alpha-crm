## Goal

Integrate `zalo-bot-js` into Alpha CRM through a safe Official Account/Bot backend bridge, while adding user-visible risk controls and help text so operators understand why some Zalo automation behaviors are blocked, throttled, or require consent.

The integration must support compliant live chat, chatbot, message history, backend status, and controlled message sends. It must not turn Alpha CRM into a personal Zalo account automation tool.

---

## Key Assumptions

1. `alpha-drm` in the request means the existing `alpha-crm` Flutter project.
2. Flutter cannot import `zalo-bot-js` directly. Integration requires a Node.js service that uses `zalo-bot-js`, while Flutter talks to that service through HTTP/SSE or WebSocket.
3. The first implementation should be mock-compatible and safe-by-default. Risky flows stay blocked unless they can prove official channel, consent, quota, and user interaction rules.
4. Existing project style is feature-first Flutter with Riverpod, shared widgets, and tokenized UI.
5. Existing Alpha CRM routes and mock screens remain in place; this SPEC adds integration and guardrails without removing screens.

## Policy / Risk Constraints

Use these constraints as product requirements, not just warnings:

- Zalo Community Policy allows account restriction or permanent lock for policy violations and flags spam/làm phiền behavior.
- Zalo identifies high-frequency messaging, friend requests to non-friends, and group create/share/invite activity as risky, including when done by third-party tools.
- Zalo account help lists third-party tools, emulators, abnormal activity, user reports, impersonation, annoying ads, and harmful behavior as common reasons for temporary disablement.
- Zalo OA messaging policy requires user interaction or permission before OA sends messages to users, and distinguishes consultation, transaction/template, and communication/broadcast messages.

## Architecture

```text
Alpha CRM Flutter UI
  -> Zalo integration API client
  -> Node.js zalo-bot-service
  -> zalo-bot-js SDK
  -> Official Bot/OA API
  -> webhook/polling updates
  -> service event store / status endpoint
  -> Flutter live chat, chatbot, history, dashboard
```

The Node service is the only layer that knows the Zalo token and calls `zalo-bot-js`. Flutter stores only UI settings, backend URL, compliance settings, and public status.

---

## Non-Goals

Do not implement:

- Personal Zalo QR/session automation.
- Emulator/device automation.
- Proxy/account rotation for personal accounts.
- Automated friend requests.
- Automated group join/invite/create campaigns through personal accounts.
- Group member scraping for outreach.
- Sending to imported phone lists without opt-in and an official approved channel.

Existing screens for these workflows may remain as CRM UI, but production execution must be blocked by risk controls unless the action is redesigned as an official/consent-based flow.

**Action:**

Create a minimal Node TypeScript backend that uses the reference SDK locally during development:

```json
"dependencies": {
  "zalo-bot-js": "file:../../../../2.reference_pj/Zalo-ref/zalo-bot-js"
}
```

Use native Node HTTP first to avoid unnecessary backend framework decisions.

Required endpoints:

- `GET /health`
  - returns service status and version.
- `GET /api/zalo/status`
  - returns bot initialized, polling/webhook mode, current safe mode, and last event timestamp.
- `POST /api/zalo/webhook`
  - validates secret header, calls `bot.processUpdate(payload)`, stores a lightweight event record.
- `POST /api/zalo/test-send`
  - only sends to allowlisted admin/test UID from env.
- `POST /api/zalo/send-message`
  - rejects by default unless request includes official channel metadata, consent proof, recent interaction metadata, and compliance pass.

Required environment variables:

- `ZALO_BOT_TOKEN`
- `ZALO_BOT_LANG=vi`
- `ZALO_WEBHOOK_SECRET`
- `ZALO_ALLOWED_TEST_UIDS`
- `PORT=8787`
- `OFFICIAL_API_ONLY=true`

`src/compliance.ts` must mirror the Flutter guard at backend level. The backend is the enforcement boundary; Flutter settings are advisory unless persisted/sent to backend.
